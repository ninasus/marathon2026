# Owner submission of consolidated group pre-order

## Requested behavior

Add `POST /group-reservations/{groupReservationId}/submit` with JSON body `{ "reservationId": "..." }`. The authenticated owner of that reservation confirms the group pre-order. Read only `GuestSession` records for the group where `IsSubmitted` is true, combine their `Dishes`, sum quantities by `DishId`, and return an array of `{ "dishId", "quantity" }`. Save the consolidated items in the existing order, set its status to `SubmittedByCustomer`, then set the group reservation status to `Submitted`.

## Scope and affected code paths

- Add a request/response model and handler under `dnapp/lambdas/api-handler/Models/GroupReservation` and `Handlers/GroupReservations`.
- Add a focused consolidation method to `IGroupReservationService` and `GroupReservationService`, using existing group, reservation, guest-session, and order repositories. Persist the order and group with separate calls using the existing `SaveOrderAsync` and `SaveGroupReservationAsync` methods. The guest-session group index and order reservation index already exist, so no new DynamoDB schema or repository method is needed.
- Register the exact requested route in `Routing/RouteRegistry.cs` and its Cognito-authorized POST method in `deployment_resources.json`. Align the existing Swagger description, which currently documents a different, unimplemented `/guest/groups/{groupReservationId}/submit` path.
- Add xUnit service, handler, and route/configuration coverage in `Tests`.

## Test strategy and acceptance criteria

- A successful owner request returns one array entry per distinct dish ID, with quantities summed only from submitted sessions, and persists exactly those items to the reservation's existing order.
- The order is `SubmittedByCustomer` and the group reservation is `Submitted` after both persistence calls succeed. The endpoint never returns 200 when either call fails.
- Unauthenticated callers receive 401; other authenticated callers receive 403. Missing group or reservation and an already `Submitted` group receive 404. A `Closed` group receives 409. All specified invalid submission conditions receive 400.
- Handler route, Cognito method configuration, Swagger path, solution build, full xUnit suite, and independent review are complete.

## Material risks and choices

- Replacing the order's dish list makes the approved group selection the canonical snapshot and avoids duplicate quantities on retry. The order must already exist; this endpoint does not create it.
- The two writes are **not atomic**. If saving the order fails, the group remains `Open`. If saving the group fails after the order succeeds, the order can be `SubmittedByCustomer` with consolidated dishes while the group remains `Open`; the request returns an error. A retry while the group is `Open` recalculates the submitted sessions and **replaces** the order dish list, so it does not add duplicate quantities, then attempts the group update again. Once the group is `Submitted`, a retry returns 404 and makes no further writes.
- Direct `SaveGroupReservationAsync` uses the loaded group object without a condition on the persisted status. Concurrent requests can both read `Open`, each save its own order snapshot, and both write `Submitted`; a stale loaded group can also overwrite a concurrent status or another group field. The 404 rule applies when this endpoint **reads** a group already `Submitted`, but a transition after that read cannot reliably be detected or mapped to 404 with direct saves. Guest-session reads can also race with guest edits. Guaranteeing one immutable snapshot across these races would require conditional writes or a broader locking/version scheme, which is outside this simplified plan.
- The user-supplied route is authoritative, despite the different path already present in Swagger. Existing customer `POST /orders/{reservationId}/submit` remains separate.
